# 滩涂拾遗：接入 AI 的产品机会研究

> 结论先行：AI 不应把滩涂拾遗改造成通用聊天工具，而应增强现有的三个核心动作——**找回、理解、记住**。最值得先做的是「语义找卡」「问题面」「遗忘后的回忆支架」。它们分别补强搜索、回顾和消化闭环，并能保持本地优先、用户可控、来源可追溯。
>
> 配套一手资料见 [`ai-product-capabilities-primary-sources.md`](./ai-product-capabilities-primary-sources.md)。本文是对本产品的推论与落地优先级，不打断 v0.2 的同步/回顾主线。

## 1. 研究范围

本报告基于当前仓库中的产品定义与实现：

- `PRODUCT.md`：核心用户是微信读书重度用户，产品服务于“重新遇到并消化”自己的划线与想法；
- `README.md`：已有同步、全文搜索、星标/标签、卡片编辑和简化 SM-2 回顾，采用 Tauri + React + Rust + 本地 SQLite；
- `docs/PRD-v0.2-review-loop.md`：近期主线是先把同步可靠性、回顾评分、队列治理和完成反馈做扎实；AI 摘要、问答和自动制卡明确不属于 v0.2，但 P2 候选已点名「AI 问题面」；
- `src/App.tsx`、`src-tauri/src/db.rs`：当前搜索是 FTS5 trigram/LIKE；回顾翻面前没有具体问题；已有按书范围、标签、星标、排除回顾、`user_version` 迁移和 0600 Key 文件模式。

因此，本报告讨论的是 **v0.2 核心闭环稳定之后** 的 AI 增强方向。

## 2. AI 应该承担什么角色

### 2.1 产品原则

1. **AI 是编者，不是作者**：整理、连接、提问、解释用户已有内容，不替用户虚构“读过什么”。
2. **先增强高频动作，不新增长驻入口**：AI 应出现在搜索框、卡片编辑和翻牌回顾中，而不是先增加一级“AI 对话”导航。
3. **生成物必须可追溯**：每个答案、主题、解释都能回到原始卡片；资料不足时明确说“不足以回答”。
4. **默认不静默改库**：自动标签、问题面等先预览，用户接受后才保存；原文永远不被覆盖。
5. **坚持本地优先**：优先在本机完成索引、召回、缓存和派生数据管理；调用云模型时只发送完成当前动作所需的最小范围。
6. **AI 不直接接管 SRS**：调度继续由稳定、可解释的算法和真实评分负责。

### 2.2 适合本产品的 AI 能力层

| 能力层 | AI 做什么 | 产品意义 |
|---|---|---|
| 召回层 | embedding、语义相似度、聚类、分类 | 找到“记得意思但不记得原词”的卡，连接跨书内容 |
| 生成层 | 问题、解释、对比、提纲、标签建议 | 把被动摘录变成可主动回忆、可继续思考的材料 |
| 检索增强生成 | 先取用户卡片，再生成带来源的回答 | 降低幻觉，让回答落回用户自己的笔记 |
| 个性化层 | 利用评分、星标、编辑、排除等反馈调整建议 | 逐渐理解什么对用户重要，但不篡改调度 |

OpenAI 官方将 embeddings 的用途列为搜索、聚类、推荐、异常检测和分类；语义检索可在几乎没有关键词重合时找到概念相关内容，正好补足当前字面搜索的边界。[OpenAI Embeddings](https://developers.openai.com/api/docs/guides/embeddings) · [OpenAI Retrieval](https://developers.openai.com/api/docs/guides/retrieval)

行业量产知识库 AI 已收敛为八种模式：来源接地问答、上下文内写作、自动结构化、学习材料再生产、跨库连接、工具调用、个性化记忆、端侧推理。对本产品最贴合的是 **学习材料再生产 + 混合检索 + 端侧/BYO-Key**，而不是开放聊天或跨库连接。详见配套一手资料 §2–§3。

## 3. 第一梯队：直接增强核心闭环

### A1. 意念检索：记得意思，也能找回原卡

**用户问题**：用户只记得大意、情绪或相关概念，却不记得原文措辞；FTS/LIKE 只能解决字面命中。

**产品形态**

- 保留现有搜索框，不新增入口；
- 搜索结果区分“原词命中”和“意思相关”；
- 继续继承当前书、标签、星标范围；
- 支持“找相似卡”，从单卡展开跨书关联。

**示例**

- 查询“人为什么会为已经投入的东西继续付出”，找到含“沉没成本”但不含查询原词的划线；
- 在一本书内搜“作者对自由的担忧”，召回不同章节的相关卡；
- 从一张“长期主义”卡片找到另外三本书中的相似或冲突观点。

**为何需要 AI**：embedding 能带来传统全文检索不具备的概念匹配、相关卡推荐和主题聚类。Azure/Anthropic 官方都把“词法 + 向量 + 融合”视为成熟检索形态；现有 FTS5 正好是词法腿。

**价值**

- 直接兑现“半年前的划线能在几秒内找到”；
- 无生成幻觉，信任成本低；
- 同一索引可复用给问答、主题页和回顾支架。

**指标**：建立 30–50 条“只记得意思”的离线查询集；比较混合检索与纯 FTS 的 `Recall@5`；观察语义结果点击率和找到目标所需时间。

**阶段**：AI 基础能力，最适合作为第一个实验。实现上可先上“相关划线”，再打开搜索入口。

### A2. AI 问题面：把摘录变成主动回忆

**用户问题**：当前翻牌前没有具体问题，回顾更像“再次阅读”而不是主动提取记忆。v0.2 PRD 的 P2 已点名该候选。

**产品形态**

- 在卡片编辑或回顾中提供“生成问题面”；
- 生成 1–3 个候选：概念问答、填空、为什么/如何、反例辨析；
- 用户预览、编辑、接受后保存；原始划线作为答案面，永不替换；
- 默认只为星标、带个人想法、或用户主动选择的卡生成；
- 未采用的问题不进入回顾，不制造大量新债务。

**示例**

原文：“人不是拥有习惯，而是由习惯塑造。”  
候选问题：“这段话如何解释‘身份’与重复行为之间的关系？”

**为何需要 AI**：问题质量依赖上下文、句式和概念理解，规则模板只能机械挖空。Gemini Notebook 把来源转成 flashcards/quizzes；Claude 学习模式强调引导推理而非直接给答案。对本产品，正确形态是“把划线变成考题”，而不是替用户读完。

**产品护栏**

- 不一次性为整个库自动生成；
- 对缺少上下文、纯抒情或不可问答的卡，允许输出“不适合生成问题”；
- 保存模型、提示词版本、输入哈希；卡片变化后标记问题面可能过期。

RemNote 官方也强调：用户自己写的卡通常效果最好，AI 卡更适合作为起点；生成后应先预览、取消不需要的卡，并进入独立“待学习”队列，而不是立刻混入到期队列。[RemNote：Generating Flashcards with AI](https://help.remnote.com/en/articles/10102901-generating-flashcards-with-ai)

**指标**：候选采用率、采用前编辑率、7 日后保留率；有/无问题面的评分分布和翻牌耗时；用户对“具体、可答、忠于原文”的主观评价。

**阶段**：先做单卡按需生成，再做小批量。这是最贴近北极星 WERU 的 AI 能力。

### A3. 遗忘后的回忆支架：只在“忘了/困难”时出现

**用户问题**：忘记一张卡时，仅再看原文未必能理解为什么忘、如何与已知内容连接；但作答前显示解释又会破坏主动回忆。

**产品形态**

- 用户选择“忘了”或“困难”后，提供“换个角度”；
- 支架可包含一句白话解释、同书联系、易混概念、具体例子或记忆线索；
- 优先从本卡、同章节、个人想法和 1–3 张相关卡中生成；
- 结论标出来源卡；结果按输入哈希缓存。
- 规则版可先上：同章相邻划线 + 用户旧 note。AI 只在材料不足时补一句。

**为何需要 AI**：解释类型需要根据卡片和失败情境动态选择，相关卡召回与针对性重述是规则系统难以覆盖的。

RemNote 的 Flashcard Insights 同样把 AI 用于卡片后的背景、上下文、近似概念，并允许仅在忘记时显示；派生内容按卡缓存、编辑后再生成，可控制延迟与成本。[RemNote：Flashcard Insights](https://help.remnote.com/en/articles/10103365-flashcard-insights)

**指标**：支架打开率、有帮助评分、下次到期成功率变化、每次有效帮助的成本与延迟、错误举报率。

**阶段**：依赖语义召回和可追溯生成，排在前两项之后。规则版可更早搭车。

## 4. 第二梯队：知识连接与输出

### B1. 主题线索 / 跨书策展

把相关卡组织成一条可阅读的“主题线索”：共同观点、分歧、例证、用户想法，每一段都链接来源卡。它不是自动文件夹，而是可随时重算的临时专题。

### B2. 基于自己的卡片问答

明确限定为“问这本书的笔记 / 问当前范围”。回答由检索出的卡片支持，并逐句或逐段引用；资料不足时拒答。NotebookLM 的产品级设计是“来源里没有就不回答”。

Anthropic 官方 citations 能将回答声明映射到文档中的字符、页码或自定义内容块位置，说明“带来源生成”在 API 层可实现。[Anthropic Citations](https://platform.claude.com/docs/en/build-with-claude/citations)

产品没有完整书籍正文，只有用户划线和想法，因此只能叫“问我的笔记”，不能包装成“问整本书”。

### B3. 选卡成稿

用户选中一组卡片，AI 生成带来源的提纲、观点—证据表、读书札记初稿或待补问题。它能把“找回和消化”延伸到表达，但当前产品明确“重读轻写”，不应让写作工作台喧宾夺主。想法润色只应在用户已有草稿时出现，且必须 diff 确认。

### B4. 标签建议、重复卡检测和低价值队列建议

- 给单卡建议 1–3 个已有标签；
- 找出高度相似卡，建议合并或互链；
- 识别过短、无上下文、长期反复“忘了”的卡，建议补问题或移出回顾。

只建议、不静默执行；对“低价值”的判断必须可撤销。规则版可覆盖相当一部分场景；全书批量出网是所有候选里隐私最重的路径，必须显式确认。

## 5. 暂不建议优先做

| 候选 | 不优先的原因 |
|---|---|
| 通用聊天框 | 入口宽泛，容易回答模型常识而不是用户笔记；需要先解决检索、引用、拒答和范围；新增一级导航会破坏克制的信息架构，并稀释北极星 WERU |
| 全书摘要 | 当前数据不是完整书稿，只能生成“我的笔记摘要”；摘要会替代而非增强消化过程 |
| 全库自动制卡 | 重新制造 v0.2 正在解决的队列债务；模型不知道什么对具体用户值得记忆；错误问题会污染回顾数据 |
| AI 直接决定 SRS 到期时间 | 模型不稳定且缺少记忆概率校准；调度应由确定性算法和真实评分负责 |
| 每日 AI 摘要/金句 | 容易变成新 feed，与安静、耐读、非碎片化浏览的产品性格冲突 |
| AI 重写划线原文 | 同步以远端原文为权威，本地重写会被 upsert 覆盖，也会篡改阅读史料 |
| AI 书童人设 / 语音 / 自动知识图谱 | 与“安静、可信、藏书人气质”冲突；图谱需要重构信息架构。相关划线是它的克制版 |

## 6. 推荐 MVP：三个功能

落地顺序建议：**AI 网关底座 → 单卡问题面 → 相关划线 / 语义找卡**。遗忘支架可先用规则版，AI 增强随后跟上。

### MVP-0：BYOK AI 网关

设置页新增独立 AI 节：OpenAI 兼容 endpoint + Key，或指向本机 Ollama/LM Studio。默认关闭；每次只发送完成当前动作所需的最小文本；结果全部缓存本地；无 Key 时入口隐藏。这是其余功能的共享依赖，也是隐私承诺的技术兑现。

### MVP-1：语义找卡 + 相似卡

本地为可见卡生成 embedding；搜索时混合 FTS 与向量相似度；单卡可查看少量相关卡。低幻觉、高复用，直接增强既有搜索。可先上“这条划线的朋友”，再打开搜索入口。

### MVP-2：单卡 AI 问题面

用户手动触发；每次给 2–3 个候选；可编辑、采用、删除；未采用内容不进回顾。它把 AI 嵌入每日回顾闭环，且风险可由“小范围 + 人审”控制。

### MVP-3：“忘了/困难”后的回忆支架

评分后按需生成一句解释 + 一个例子或相邻概念 + 来源卡；结果缓存。它把 AI 放在最明确的困难时刻，也为以后“问我的笔记”复用检索与引用能力。

### MVP 共同验收门槛

1. 不新增一级 AI 导航；
2. 原卡不被自动覆盖，生成结果可删、可编辑；
3. 每次云调用前能解释发送范围，设置中可关闭；
4. 所有生成结果记录来源卡和生成版本；
5. 离线时原有搜索、浏览、编辑、回顾完全可用；
6. AI 失败只影响增强功能，不阻塞核心流程。

## 7. 技术路径

### 7.1 推荐的混合本地架构

```text
SQLite 原卡
   │
   ├─ 内容哈希 ──> 本地 embedding 服务 ──> 本地向量索引
   │                                      ├─ 语义搜索/相似卡
   │                                      └─ 为生成任务召回上下文
   └─ 用户明确触发 ──> 最小上下文包 ──> 本地或云端生成模型
                                           └─ 结构化结果 + source_card_ids
                                                       └─ 预览/接受/缓存/删除
```

- 字面搜索继续走 FTS5，语义搜索与其混合排序而非替换；
- 典型 100–5000 张卡可先用简单向量扫描验证价值，再决定是否引入专用向量扩展；
- 卡片正文、批注、书名或章节变化后增量更新 embedding；隐藏卡从结果中过滤；
- 用 provider adapter 隔离模型供应商；
- 可支持 Ollama。其官方接口能批量生成 L2 归一化 embeddings，并建议用余弦相似度，适合语义搜索、检索和 RAG。[Ollama Embeddings](https://docs.ollama.com/capabilities/embeddings)

### 7.2 Apple 端侧模型

Apple Foundation Models 官方文档列出摘要、实体抽取、文本理解、结构化输出和工具调用等能力，端侧模型能让数据留在设备上。但当前要求较新的 macOS、设备支持 Apple Intelligence，相关 API 仍在演进，且官方明确端侧模型“不为世界知识与高级推理设计”。[Apple Foundation Models](https://developer.apple.com/documentation/foundationmodels)

因此它适合作为 macOS 增强 provider，而不是唯一依赖：项目还发布 Windows/Linux，Tauri/Rust 也需要 Swift 原生桥接。首版应先定义统一 `EmbeddingProvider` / `GenerationProvider` 契约。

### 7.3 建议数据模型

```text
card_embeddings
- card_id
- provider / model / dimensions
- content_hash
- vector
- updated_at

ai_artifacts
- id
- artifact_type       # question_face / review_scaffold / topic_brief
- source_card_ids
- input_hash
- provider / model
- prompt_version
- content_json
- status              # proposed / accepted / rejected / stale
- user_edited
- created_at / updated_at
```

不要把 AI 问题直接塞进 `cards.text` 或 `note`：原始内容、用户内容和模型派生内容需要独立生命周期，才能处理重新生成、过期、删除和来源追踪。所有 schema 变更继续走现有 `user_version` 幂等迁移。

## 8. 隐私、可信与成本

- 本地索引默认开启或明确初始化；云生成默认关闭，由用户选择 provider；
- 调用前展示将发送“当前卡 / 同章节 N 张 / 相关卡 N 张”，不上传整库；
- 提供“删除全部 AI 派生数据与索引”，日志不记录正文、prompt 或完整响应；
- AI 产物明确标为“建议问题”“相关线索”“AI 解释”，不伪装成原文；
- 无支持证据时允许空结果；提示词或模型升级后旧产物不自动覆写；
- embedding 只在内容变化时重算；问题面和支架按输入哈希缓存；
- API Key 复用或加强现有本机 0600 凭据保护模式；
- 接云 API 即引入厂商留存与子处理条款，必须明示。纯端侧则天然为空集。

三条设计底线：

1. 任何 AI 产出必须可回溯到原文，不可回溯就不上；
2. AI 产出先入草稿/建议态，人确认后才成为正式字段；
3. 默认端侧或显式 BYO-Key，绝不静默上传。

## 9. 验证计划

### 阶段 0：离线验证（1 周）

- 整理 30–50 个“只记得意思”的真实脱敏查询；
- 比较 FTS、embedding、混合排序；
- 为 50 张卡制定“好问题/坏问题”人工准则；
- 退出条件：语义检索明显提升 `Recall@5`，问题面具备稳定质量标准。

### 阶段 1：内部可用（1–2 周）

- 设置中手动配置 provider；
- 上线语义搜索实验开关和单卡问题面；
- 所有生成结果必须预览；
- 只记录采用、编辑、拒绝、延迟、失败等本地匿名指标。

### 阶段 2：5–20 人灰度（2 周）

验证：能否找回关键词搜不到的旧卡；问题面是否促成主动回忆；用户能接受什么出网范围；哪类遗忘支架有效；是否理解 AI 内容与原始笔记的区别。

### 建议放行阈值

- 语义搜索 `Recall@5` 显著高于纯 FTS；
- 问题候选采用率 ≥60%；
- 支架“有帮助”率 ≥70%；
- 生成内容来源关联正确率 ≥95%；
- AI 关闭或离线时核心浏览、搜索、回顾零退化；
- 无任何未经确认的原文覆盖或批量入队。

## 10. 优先级结论

| 优先级 | 特性 | 用户价值 | 风险 | 建议 |
|---|---|---:|---:|---|
| 0 | BYOK AI 网关 | 基础设施 | 低 | 其余功能的前置 |
| 1 | 意念检索 + 相似卡 | 高 | 低—中 | 首个低幻觉实验；相关划线可先上 |
| 2 | 单卡 AI 问题面 | 高 | 中 | 最贴近 WERU；人审后保存 |
| 3 | 遗忘后的回忆支架 | 高 | 中 | 规则版可更早；AI 增强随后 |
| 4 | 主题线索 / 跨书策展 | 中—高 | 中 | 第二阶段差异化能力 |
| 5 | 问我的笔记 | 中—高 | 中—高 | 检索与引用成熟后 |
| 6 | 标签建议 / 重复检测 | 中 | 低—中 | 规则先行，向量增强随后 |
| 7 | 选卡成稿 / 想法润色 | 中 | 中 | 不抢“重读轻写”主线 |
| 暂缓 | 通用聊天、全书摘要、全库自动制卡、AI 调度 | 不确定 | 高 | 不作为首发 |

最终判断：**AI 的差异化不在“它也能聊天”，而在于它能以用户自己的划线为证据，让一条旧笔记更容易被找到、被主动回忆、被重新理解，并在不同书之间发生连接。**
